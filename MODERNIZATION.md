# ZAMI — modernised front-end: how it works

The site is still a **static GitHub Pages site talking directly to Supabase**. Nothing about the
backend changed (tables, views, RPCs, storage buckets, edge function, auth, env/keys are all as before).
What changed is the front-end structure.

## The big idea

Every old URL still exists (`browse.html`, `detail.html?type=…&id=…`, `artist.html?id=…`, `login.html`,
`account.html`, `checkout.html`, `balance.html`, `my-uploads.html`, `upload.html`, `admin.html`,
`download.html`). Each is now a ~20-line bootstrap file that loads **`app/main.js`**. So:

* direct links, refresh, shared links and the **Android app's start URL (`browse.html`) work exactly as before**
* inside the app, same-site links are intercepted and rendered **without reloading the document**
* the shell (header, bottom nav, **one `<audio>` element**, mini player) is created once and never torn down,
  so **music keeps playing while you navigate**

`index.html` (landing page) and `street-rush.html` (the game) are untouched standalone pages
(index only swaps its 830 KB logo for a 13 KB copy).

## Layout

```
app/
  main.js              entry: builds shell, mounts player UI, starts router
  lib/
    router.js          path-compatible router (popstate, scroll restore, per-view cleanup, error/loading states)
    supabase.js        THE shared Supabase client (same URL/anon key/CDN import as before) + cached getUser()
    api.js             data access: the same queries the old pages made, plus TTL cache + de-duplication
    cache.js           tiny TTL / in-flight-dedupe / stale-fallback cache
    favorites.js       shared favourites state (one load, one toggle implementation)
    store.js dom.js promo.js
  player/player.js     the ONE audio element + queue, shuffle, repeat, volume, errors, Media Session, play counts
  ui/                  shell.js, player-ui.js (mini bar + now-playing sheet), cards.js, waveform.js, icons, toast
  views/               one module per page
    browse.js detail.js artist.js        rebuilt on the shared components
    account.js login.js checkout.js balance.js my-uploads.js upload.js admin.js download.js
                         ADAPTER views: the original page logic, unchanged, generated by tools/convert-page.mjs
  css/shell.css        tokens + shell + shared components (all classes prefixed zs-)
  css/views/*.css      per-view CSS, scoped under #zs-view so views can never leak into each other or the shell
legacy/                originals for rollback: legacy/original/*.html, plus the stale copies that used to be in the repo root
tools/                 convert-page.mjs, scope-css.mjs, build-view-css.mjs (+ css-src/ for hand-written view CSS)
tests/                 e2e.py, compare_adapters.py, stub-supabase.js (TEST-ONLY), test audio
```

## Persistent player — rules it follows

* exactly one `<audio id="zs-audio">`, created in `player.js`, living in the shell; views never create audio
* the router only swaps the content area; it never touches the shell or the audio element
* clicking the track that is already loaded toggles play/pause (never reloads); rapid clicks while a track is
  resolving are ignored; a stale async resolve can never override a newer track (sequence token)
* free tracks stream the full file, paid tracks/beats stream the preview clip (same rule as before)
* failed/offline audio → error state with Retry; in a queue it auto-skips to the next playable item
* play counting uses the same `increment_play_count` RPC, once per started play
* Media Session (lock screen / headset / notification) title, artist, artwork, play/pause/next/prev/seek
* nothing is preloaded: `preload="none"`; audio is fetched only when you press play
* the detail-page waveform is drawn natively (same look as the old WaveSurfer) from low-sample-rate decoded peaks,
  cached per URL, skipped under Data Saver; it only seeks the shared audio — it can't create a second player

## Caching & performance

* one Supabase client and one cached `auth.getUser()` for the whole session (was: one client + one network call *per page*)
* TTL cache with in-flight de-duplication: featured artists 5 min, trending/top downloads 2 min, first feed pages 45 s,
  items 30 s, track audio URLs 10 min; back/forward restores the exact feed + scroll with **no refetch**
* search is debounced (was: a request per keystroke, and responses could arrive out of order)
* realtime subscriptions are removed when you leave Browse; top-downloads refresh is debounced
* images are `<img loading="lazy" decoding="async">` with fixed aspect ratios (no layout shift)
* the page-level JS is split per view and loaded on demand; the shell loads `preconnect`/`modulepreload` hints
* WaveSurfer (esm.sh) is no longer loaded — one fewer third-party host

## Security notes

* user-generated strings (titles, names, bios) are always inserted as text, never parsed as HTML in the rebuilt views;
  image URLs must be http(s) (`safeUrl`). This closes an injection path that existed in the old browse page.
* the Supabase **anon key is public by design**; real protection is Row Level Security and storage policies, which live in
  your Supabase project, not in this repo. See DEPLOY.md → "Recommended follow-ups".

## Adding a new page

1. create `app/views/<name>.js` exporting `title`, `css` (optional), `markup` (optional) and `async mount(ctx)`
   (`ctx.supabase`, `ctx.params`, `ctx.state`, `ctx.onCleanup(fn)`, `ctx.navigate(url)`, `ctx.ready()`)
2. add the route in `app/lib/router.js` (`ROUTES`)
3. add a bootstrap `<name>.html` (copy `browse.html`)

## Running the tests

```
python3 -m http.server 8765 --directory <folder containing a symlink "Music" -> this repo>
python3 tests/e2e.py              # routing, persistent player, caching, search, detail, mobile, security
python3 tests/compare_adapters.py # converted pages vs. untouched originals, same backend stub
```
The tests use a **stub** of Supabase and generated audio. They prove the front-end behaviour; they do not
exercise your live database, OTP SMS, storage or MoMo flows (see DEPLOY.md → manual checklist).
